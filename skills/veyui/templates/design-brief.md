# Design brief

Replace prompts with project evidence. Keep only applicable sections. This is a working decision record, not a questionnaire to send wholesale.

## Goal and scope

- Audience, situation and primary task
- User-requested finish line and existing approvals/delegation
- Entry points, actual behavior and preserved contracts
- Fixed rules / inherited defaults / authorized changes / unresolved assumptions
- Available rendering, interaction and asset tools

## Reference direction shortlist

- Recommend / user references / combine; project-fit criteria
- Three directions, each with an actual existing public link, access check, specific region, evidence basis, adaptation and tradeoff
- Recommendation and actual direction choice/delegation; target palette chosen independently
- Mapping from each generated concept to existing-example links and its own preview URL

## Research and experience

- Selected reference records with actual observations and evidence type
- Palette-free concept extraction and source-to-target translation; target palette authority recorded separately
- Selected pattern IDs, why they fit and what must be adapted
- Task path and important alternate/recovery path
- Information architecture and representative content
- Existing usability issues with baseline evidence

## Quality and direction decisions

- Chosen reference, intended visual character and any default recipe it overrides
- Strict quality safeguards and platform mapping
- Product-specific message, truthful proof and actual next action for each section/screen
- Candidate comparison across composition, identity, UX, content framing and motion
- Complete landing-page or representative end-to-end task coverage required for all candidates
- Lead, independent visual reviewer and UX/engineering reviewer, or explicit tool-limited fallback

## Craft decisions before construction

Apply the seven passes to the representative screen or section. Share decisions across related screens where appropriate. Record concrete values and relationships, then link to the rendered checks in the review record.

| Pass | Project decision and rationale | Rendered state/check |
|---|---|---|
| Focal hierarchy | Immediate task, dominant area and primary/secondary actions | |
| Spacing | Scale, related versus separate group gaps and alignment edges | |
| Typography | Roles, weights, tones, sizes, measure and font/fallback behavior | |
| Color | Neutral/surface roles, emphasis, focus, status and approved expressive use | |
| Content | Specific benefit/task copy, sources, coherent fixtures and proof boundary | |
| Details | Nested radii/insets, borders/elevation, icon family and optical alignment | |
| Motion | Trigger/object/origin, enter/exit, interruption and reduced-motion result | |

## Candidate design briefs

For each candidate record the organizing idea, composition, actual typography and color roles, spacing/geometry, imagery strategy, motion storyboard and compact adaptation. Attach reviewed full-page/task coverage and readable detail views, including compact adaptations. Identify substantive differences and tradeoffs. Do not call prose alone a visual prototype.

## Assets and dependencies

- Existing asset sources, rights, crop and fallback
- Proposed generated assets and explicit permission status
- Component need, existing/native alternative, selected exact item, access/license and dependency impact
- Performance budget derived from project needs and measurement method
- Staged product demonstration applicability and reason; for applicable scenes, product evidence, placement/crop, storyboard, simulation boundary, compact layout, reduced-motion poster and rehearsal evidence

## Selected design contract

| Requirement ID | Decision / expected behavior | Component or screen | States and adaptation | Verification evidence |
|---|---|---|---|---|

Record selected artifact/version, rationale, approval/delegation and any unresolved material choice. Keep one source of truth for tokens and component anatomy. Map implementation tasks to these requirements only when implementation is in scope.

## Review and handoff

- Actual captures and interaction results
- Highest-impact defects, corrections and rechecks
- Applicable built-in review findings and unresolved blockers
- Delivered scope and next authorized action

## Public-page content strategy (when applicable)

Use `product-story.md` alongside this brief: cross-project coverage and feature evidence; audience, priority benefits and buying objections; actual message angles; complete page copy; proof/claim mapping; exclusions and release/plan limits. Preserve an existing approved positioning. Integrate with section-level visual-medium decisions before layout is fixed.
