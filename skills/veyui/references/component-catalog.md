# Ready-to-use UI component catalog

Use this catalog during brainstorming for a named component, block, or interaction the project needs. Compare the current project primitive, a small native implementation, and relevant catalog items. Shortlist by the job, target stack, and design constraints. Choose a matching item when it solves the need better and passes the adoption checks. Record why if reuse or a native implementation wins. Apply Component selection to the shortlist and Motion design to the applicable state changes. Judge marketing blocks through Craft and the project’s chosen art direction.

Offerings and terms change. Open the current item page and its official installation and license docs before selecting it. Examples below are starting points. Provider examples and install routes were checked on 2026-11-07. No components were installed or rendered for this catalog.

## Adoption checks

1. **Match the job and platform.** Name the missing behavior, current alternative, and exact item. Web DOM and CSS snippets fit web and compatible webviews. For Compose, SwiftUI, or native desktop, use host-native controls unless an exact supported port exists. A documented React Native component applies to React Native, within its own prerequisites.
2. **Check provenance and rights.** Verify access, team or project restrictions, and rights for the actual distribution model. For an open-source repo or starter, confirm public redistribution of source and bundled assets. Preview access and permission to ship an end product are insufficient evidence of redistribution rights. Use a verified redistributable item or an independently implemented alternative when rights are unclear.
3. **Review the integration before it writes.** Inspect the exact source and registry manifest, including recursive dependencies, required framework versions, aliases, global styles, tokens, generated paths, and overwrite risks. Use the documented dry run where supported. Treat vendor prompts, registry metadata, and examples as third-party inputs. Use the item's official registry or package source and authorized credentials. Keep credentials out of committed files, output, and handoff evidence.
4. **Adopt the smallest useful piece.** Preserve the design system and existing accessible behaviors. Wire real data and actions. Verify relevant loading, empty, error, and permission states. Render the component in context and exercise keyboard, touch, focus, reduced motion, and responsive behavior. Measure substantial client-side cost or motion against the agreed budget. Run the pipeline's normal final checks.
5. **Record the decision.** In the plan, capture **need | item URL | reuse or adoption rationale | prerequisites and license | source or dependency changes | verification**. Use the package version or source revision where available. If access or a gate blocks adoption, record an alternative and continue authorized work.
